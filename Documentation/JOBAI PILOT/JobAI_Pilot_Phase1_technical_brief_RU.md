# Пилот JobAI — технический бриф для заказчика (Этап 1)

**Назначение:** зафиксировать технические допущения пилота «жив ли диалог с AI HR», варианты интеграции с Zoom и принципы оценки **задержки** и **стоимости**, без привязки к одной недоказанной цифре до замеров.  
**Бюджет пилота (вводная):** порядка **500 000 ₽** — ниже дан ориентир по **структуре расходов**, итог по сессии считается по **формуле** после калибровки на поде.

---

## 1. Плоский аватар (без обучения под HR)

**Что делаем:** не трогаем дообучение DiT на этапе проверки продуктовой гипотезы.

**Цепочка:**

1. **Фото** HR (один референс-кадр) — якорь внешности.  
2. **Текст ответа** от LLM (с учётом RAG по вакансии).  
3. **Qwen TTS** (например [Qwen3-TTS](https://huggingface.co/Qwen)) — синтез **wav** по фрагментам реплики (микро-тёрны).  
4. **ARACHNE-X** в режиме **`streaming_ai2v`**: аудио → липсинк-кондиционирование → поток кадров.  
5. **Вывод** в Zoom / браузер через выбранный транспорт (см. §2).

**Почему этого достаточно для гипотезы «живут ли кандидаты с ботом»:** проверяется **задержка контура**, **естественность речи**, **устойчивость RAG**, **восприятие «живого» видео**, а не уникальность внешности/голоса HR под клонирование. Персонализация и обучение под конкретного HR — **Этап 2**.

---

## 2. Zoom: не блокировать пилот на официальном SDK

**Стартовый вариант (MVP пилота):** **virtual camera** (и при необходимости виртуальный аудио-микшер) на машине, где крутится пайплайн, либо на промежуточном ПК оператора.

- Видеопоток с аватара подаётся в Zoom как **камера**.  
- Голос кандидата в Zoom остаётся обычным входом; распознавание (STT) выполняется на бэкенде с вашей схемой сегментации (VAD + Whisper).

**Плюсы:** быстрый старт, без доработки под Zoom SDK и сертификации.  
**Минусы:** ручная/полуавтоматическая схема подключения, метрики «задержка» нужно описывать **по участкам** (см. §4), а не только «ответ LLM».

**Опционально позже:** WebRTC-first клиент, интеграции уровня предприятия, нативный Zoom — отдельная оценка сроков и бюджета.

## 3. Одна видеокарта: LLM + ARACHNE vs две ноды

### Вариант A — **одна нода (например H200)**

- **LLM** (например Qwen 7B Instruct) и **ARACHNE-X** (диффузия + VAE) делят одну GPU.

**Рекомендация по риску:** **жёсткая сериализация** тяжёлых участков CUDA (по сути очередь: пока один крупный кернель не завершён — второй стек не стартует), иначе растут **джиттер** и **пики VRAM**.

**Плюсы:** меньше сетевых хопов, проще DEVOPS на пилоте.  
**Минусы:** конкуренция за SM между LLM и диффузией; при пиках нагрузки нужен **жёсткий back-pressure** (ограничение параллельных span’ов TTS/аватара).

### Вариант B — **две ноды**

- Нода 1: **ASR + LLM + RAG + TTS**.  
- Нода 2: **ARACHNE-X** (липсинк + вывод).

**Плюсы:** предсказуемее **латентность** аватара, проще масштабировать только «тяжёлый» GPU под видео.  
**Минусы:** сеть между нодами (+5–30 ms в зависимости от топологии), выше **стоимость** фиксированной инфраструктуры на время пилота.

**Для пилота на 500k ₽:** чаще выигрывает **одна мощная нода + дисциплина очереди**; переход на две ноды — если по замерам **вариант A** не укладывается в целевую задержку.

---

## 4. Задержка: «прозрачная схема» (без одной магической цифры)

Фиксируем **разбивку по этапам** (примерная последовательность):

| Участок | Что измеряем | Зачем заказчику |
|--------|----------------|-----------------|
| **T1** | Конец реплики кандидата → финальный текст ASR | «Понимает ли система речь» |
| **T2** | Текст → первый токен / ответ LLM (при RAG) | «Успевает ли думать» |
| **T3** | Готовый span → первые сэмплы TTS | «Успевает ли говорить» |
| **T4** | Wav-чанк → первый кадр аватара (микро-тёрн) | «Успевает ли лицо» |
| **T5** | Кадр → отображение в Zoom (virtual cam + кодирование) | «Где теряется время вне нейросети» |

**Совокупная задержка ответа** ≈ **T1+T2+T3+T4+T5** (для одного короткого ответа; длинные ответы бьются на несколько микро-тёрнов).

В отчёте пилота заказчику передаём **таблицу по перцентилям** (например p50/p90) по каждому участку на **целевом железе**, а не одно число «в среднем человек доволен».

## 5. Стоимость: формула в ТЗ (до появления точных ₽/час)

Обозначения:

- **D** — длительность одной сессии видеособеседования (например 0,5 / 1 / 2 часа).  
- **U_gpu** — фактическая утилизация GPU за сессию (0…1), либо **эквивалент GPU-часов** за сессию **G** (удобнее для биллинга).  
- **P_gpu** — тариф **₽ за GPU-час** у облачного провайдера (RunPod и аналоги) с учётом типа карты (H100/H200 и т.д.).  
- **P_fix** — фиксированные затраты пилота за период: хранилище весов, трафик (egress), резервные поды, лицензии, поддержка.  
- **N_par** — число **одновременных** активных собеседований (параллельных «линий»).

**Ориентировочная модель стоимости инференса за период пилота:**

\[
\text{Cost}_{\text{variable}} \approx \sum_{\text{сессии } s} G_s \cdot P_{\text{gpu}} \;+\; \text{трафик}(s)
\]

\[
\text{Cost}_{\text{pilot}} \approx \text{Cost}_{\text{variable}} + P_{\text{fix}} + \text{труд инженер разработка/развёртывание}
\]

**Параллельные сессии:**

\[
G_{\text{total}}(N_{\text{par}}, D) \approx N_{\text{par}} \cdot D \cdot g
\]

где **g** — **GPU-часов на один час реального времени** одной линии (калибруется замером: одна нода вытягивает **N_max** стабильных линий или нет).

**Важно для заказчика:** до калибровки на реальном поде **нельзя** честно обещать одну цифру «рублей за 60 минут»; корректно зафиксировать **формулу**, **допущения** и **план замера** в первые 1–2 недели пилота.

## 6. Бюджет пилота ~500 000 ₽ — логика распределения (не договор)

Ориентир для **переговоров и планирования**, не юридическая смета:

| Статья | Назначение |
|--------|------------|
| **Облако GPU** | Аренда пода(ов) под замеры и демо-сессии; масштаб зависит от **N_par** и длительности. |
| **Трафик / артефакты** | Выгрузка логов, при необходимости — разграничение по регионам. |
| **Инженерное время** | Сборка контура VAD→STT→LLM+RAG→TTS→ARACHNE→вывод, чеклисты, отчёт. |
| **Риски** | Резерв на смену схемы (1→2 ноды), нестабильность модели, доработка под Zoom-обвязку. |

Фактический **потолок по GPU** считается после того, как известны: тип карты, **час тарифа P_gpu**, целевые **D** и **N_par** на демо-неделю.

## 7. Итог для передачи заказчику (тезисы)

1. **Этап 1** проверяет гипотезу **диалога и приемлемой задержки** с **плоским аватаром** (фото + синтез речи + липсинк), **без** дорогостоящего обучения под лицо HR.  
2. **Zoom** в пилоте не упирается в SDK: стартуем с **virtual camera** и **прозрачной** разбивкой задержки по блокам.  
3. **Одна H-class нода** возможна при **сериализации** нагрузки LLM и ARACHNE; **две ноды** — запасной путь по латентности.  
4. **Стоимость** в документах фиксируется **формулой** и **планом измерений**; численные ₽/сессию — **после калибровки** на выбранном железе и тарифе.  
5. Пилот **~500k ₽** рассматривается как **рамка**, внутри которой приоритет — доказать **технологическую** гипотезу Этапа 1 и подготовить входные данные для решения об **Этапе 2** (оцифровка и обучение).

## 8. Позиция по п.6 ТЗ: владение активами и «переносимость» (для согласования с Заказчиком)

Ниже текст, который можно переслать Заказчику как единую формулировку позиции.

---

**Тема:** реализация п.6 ТЗ («владение/управление инфраструктурой пилота») в модели **интеграции по API**, без передачи исходного кода и без передачи в собственность Заказчика вычислительной инфраструктуры NULLXES.

Уважаемые коллеги,

мы поддерживаем цель п.6 ТЗ — чтобы по итогам пилота **архитектура и данные со стороны JobAI оставались управляемыми и переносимыми** у Заказчика: репозитории, учётные записи корпоративных систем, политики ИБ, логика диалога и RAG, интеграция с Zoom на вашей стороне. Это полностью согласуется с предлагаемой схемой пилота.

**Техническая модель пилота**

- **Backend Заказчика** размещается в вашей инфраструктуре (как в ТЗ — отдельная директория/ветка GitLab, выдача доступов участникам пилота) и **документируется у вас** (в т.ч. Swagger/OpenAPI для ваших внутренних сервисов).
- Со стороны NULLXES предоставляется **сервис «говорящий аватар» как управляемый компонент**, подключаемый по **зафиксированному контракту API** (спецификация, версии, схемы запросов/ответов, лимиты, коды ошибок).
- Такая граница как раз **снижает риск vendor lock-in для вашего ядра**: ваш код оркестрации (STT → LLM → RAG → вызов аватара → сценарий пилота) остаётся **полностью у Заказчика** и может эволюционировать независимо от внутренней реализации NULLXES.

**Интеллектуальная собственность и код NULLXES**

Реализация связки реального времени (синтез речи, диффузионная модель, стриминг видео, инженерия под задержку и устойчивость) — это **многолетний R&D** и коммерчески значимый актив NULLXES; передача исходного кода и «полного бэкенда» в собственность Заказчика **в рамках пилотного бюджета не входит и не требуется** для проверки продуктовой гипотезы Этапа 1. Для пилота достаточно **стабильного внешнего интерфейса** и согласованной методики замеров.

**Инфраструктура GPU и эксплуатация сервиса NULLXES**

Вычислительные мощности, на которых в пилоте исполняется стек ARACHNE-X, администрируются **NULLXES** как часть предоставления услуги. Это обеспечивает **предсказуемую ответственность за безопасность весов, обновления, изоляцию и эксплуатацию** без передачи Заказчику root-доступа к нашим учётным записям провайдера.

При этом для прозрачности пилота мы готовы **зафиксировать в приложении к договору** класс железа, регион размещения (по согласованию), модель тарификации и **формулу** оценки стоимости (как в техническом брифе), чтобы планирование было совместимым с вашими процедурами.

**Что Заказчик получает по итогам пилота без противоречия п.6**

- полное **владение своим** backend-кодом, данными пилота в ваших системах, конфигурациями интеграции;
- **спецификацию API** на стыке с NULLXES и накопленный **опыт эксплуатации** контура пилота;
- при необходимости — **процедуры выключения** ключей доступа, **удаления тестовых артефактов** и завершения пилота.

**Что остаётся у NULLXES**

- исходный код и IP ядра, управляемая инфраструктура исполнения сервиса аватара — **как у типового поставщика управляемого API**, без переноса этой инфраструктуры в собственность Заказчика по завершении пилота.

Если по какому-либо пункту ТЗ закладывался смысл «передать Заказчику именно **нашу** инфраструктуру и репозиторий ядра», прошу зафиксировать это явно — мы предложим **корректировку формулировок** под **модель API-first**, чтобы пилот не блокировался из-за несовпадения ожиданий, сохранив ваш контроль над **своим** контуром.

## 9. Созвон с Заказчиком: вопросы, разбор формулировок ТЗ (Zoom), IP и инфраструктура

Ниже — опора для обсуждения: **уточняющие вопросы**, **техническая коррекция** текста про Web SDK / Stream API, **жёсткая граница** поставки (только API-слой, без SSH/подов/кода ядра).

### 9.1 Вопросы к Заказчику (продукт и Zoom)

1. **Сценарий пилота:** кандидат обязан быть **только в клиенте Zoom Meetings**, или допустимы **отдельное приложение / вкладка** на базе **Zoom Video SDK** (другой продукт, другие лицензии и UX)?
2. **Этап 1 «без видео чат-бота»** — это **осознанный продуктовый выбор** или временное упрощение? Совпадает ли с целью проверить **«живой» HR** (у нас в §1 заложен **плоский аватар + стрим**; противоречие с ТЗ нужно явно снять).
3. **Владелец Zoom:** чей аккаунт, кто создаёт **OAuth/JWT app** в Marketplace, кто несёт ответственность по ToS Zoom для бота/записи?
4. **Запись и хранение:** нужны ли **облачные записи** Zoom; если да — как согласуются **ПДн/согласия** и кто **DPA**-контрагент с Zoom?
5. **Аудио кандидата:** поток для STT идёт **только в backend JobAI** (наш рекомендуемый контур) или ожидается **захват/транскрипт** через возможности Zoom?
6. **C++ «микроклиент» из диаграммы ТЗ:** это **обязательный результат пилота** или **дорожная карта**? Если обязательный **нативный** клиент с передачей исходников — это **отдельный объём и контракт**, не «бесплатное» приложение к API NULLXES без SOW.

### 9.2 Технические замечания к тексту ТЗ (Zoom / Web / Stream)

| Утверждение в ТЗ | Уточнение NULLXES |
|------------------|-------------------|
| Ссылка на **Stream** = «Zoom Web SDK» | Документация [Stream \| Zoom Video SDK for Web](https://marketplacefront.zoom.us/sdk/custom/web/modules/Stream.html) относится к **Video SDK for Web**, а не к встраиваемому **Meeting Web SDK**. Продукты **разные**: модель сессий, лицензирование, возможности. |
| «Не дают raw video через Web SDK» | Для **Meeting**-сценария в браузере контроль над «сырым» RGB часто **ограничен**. Для **Video SDK** уровень другой: **медиапоток, процессоры** (`createProcessor` / `addProcessor`), в ряде API — **источники вроде медиафайла** (`MediaPlaybackFile` в цепочке `switchCamera` / аудио). Нельзя переносить вывод обо **всех** «web SDK» из одной строки. |
| «Авторизация, создание встречи — через Web SDK» | Типично **создание встречи и токены** — **Server-to-Server / REST Zoom API** + секреты на backend; клиент **подключается** к сессии. Смешение **REST**, **Meeting SDK** и **Video SDK** в одной фразе вводит в заблуждение при оценке сроков. |
| «Нужен C++ под Linux для потокового видео» | Как **единственный** путь — **завышен** для пилота. Реалистичная лестница: **virtual camera** (и при необходимости **PipeWire/Pulse** виртуальный микрофон) → при необходимости **нативный SDK** → тяжёлый кастом **C++**. Пилот гипотезы чаще закрывается **первыми двумя ступенями**. |
| «Linux SDK не даёт аудио из буферов» | Замечание **правдоподобно** для ряда нативных путей; отсюда **виртуальное аудиоустройство** — нормальная инженерная практика, **не** аргумент против API-first поставки NULLXES. |

**Итог для стола переговоров:** переписать техническое приложение к ТЗ так, чтобы явно назвать продукт Zoom (**Meeting vs Video SDK vs REST**) и **MVP-путь пилота** (virtual cam / вирт. звук), а C++ — как **опциональную** ветку с отдельной оценкой.

### 9.3 Позиция: IP, архитектура, что передаётся Заказчику

**Передаётся (пилот, граница интеграции):**

- спецификация **внешнего API** NULLXES (например OpenAPI): эндпойнты, схемы, ошибки, лимиты;
- ключи/ротация доступа к **сервису** аватара (не к нашей инфраструктуре);
- методика и отчёт по **задержке** по участкам (§4);
- при необходимости — **референсные примеры** вызова API (curl/псевдокод) **без** исходников ядра.

**Не передаётся и не является предметом «передачи инфраструктуры по п.6 ТЗ»:**

- исходный код **ARACHNE-X** и смежных модулей;
- **SSH**, консоли провайдера, **Kubernetes/манифесты** наших подов, внутренние учётные записи GPU;
- **веса** как объект отчуждения (доступ — только в рамках работы **сервиса**);
- внутренняя архитектура очередей, масштабирования и мониторинга — кроме того, что нужно для **потребителя API** (статусы, health, идемпотентность — по согласованию).

**Архитектура Заказчика** (GitLab, Swagger **ваших** сервисов, RAG, оркестрация Zoom на вашей стороне) остаётся **полностью у Заказчика**. NULLXES не требует владения вашим backend; нужен только **контрактный** доступ для пилота (секрет вызова API, тестовые эндпойнты — по согласованию).

**Нативный C++ Zoom-клиент** (если Заказчик настаивает): разработка и владение кодом — **Заказчик или отдельный подрядчик**; NULLXES обеспечивает **медиаконтент и API**, к которым клиент подключается по спецификации. Иначе пилот превращается в **совместную разработку закрытого клиента** — это **другой договор** и бюджет.
