# Интеграция DiT (LongCat-Video) в ARACHNE-X — архитектурное решение

**Роль:** главный AI-архитектор системы ARACHNE-X  
**Контекст:** собственная AI-экосистема (Arachne-X core, кастомный training pipeline, multi-GPU, enterprise-ориентированная архитектура).  
**Цель:** формализовать использование архитектуры и весов DiT из LongCat-Video (HuggingFace) и минимизировать риски.

---

## 1. Определение: нужны ли pretrained веса или только архитектура

| Сценарий | Веса | Обоснование |
|----------|------|-------------|
| **Base pipeline (T2V, I2V, VC)** | **Нужны pretrained** | Без инициализации от LongCat-Video инференс бесполезен; обучение с нуля 13.6B — непропорциональные затраты. |
| **Avatar pipeline** | **Зависит от стратегии** | (1) Дообучение от base DiT → нужны base pretrained + свои чекпоинты `avatar_single`/`avatar_multi`. (2) Обучение avatar с нуля → только архитектура. В текущей системе предполагается (1). |
| **Исследования / кастомные головы** | **Только архитектура** | Возможны эксперименты с своей инициализацией или другими весами. |

**Вывод:** для production-инференса и для обучения base/avatar от базы — **pretrained веса нужны**. Архитектура уже скопирована в `arachne_x/modules/` (LongCatVideoTransformer3DModel, LongCatVideoAvatarTransformer3DModel) и совместима с ключами весов HF (например `blocks.*` в `dit/diffusion_pytorch_model.safetensors.index.json`).

### 1.1 Если обучаем сами — есть ли смысл качать?

| Режим обучения | Качать LongCat-Video? | Зачем |
|----------------|------------------------|-------|
| **Base DiT с нуля** | **Нет** | Достаточно архитектуры в `arachne_x/modules/`. Инициализация — своя (например Kaiming/Xavier). Скрипт `download_longcat_video.py` не нужен. |
| **Avatar с нуля** | **Нет** | То же: только наш код, свои веса. |
| **Base DiT fine-tune / LoRA** | Зависит от базы | Если база — **ваш** ранее обученный чекпоинт: не качать. Если база — **их** pretrained: качать один раз, дальше работать со своим снапшотом. |
| **Avatar от base** | Обычно **да** (один раз) | Если base берёте от LongCat — качать нужно как стартовую инициализацию. Если base уже свой — качать не нужно. |

**Итог:** при **полном обучении с нуля** (base и/или avatar) качать веса LongCat-Video **не имеет смысла** — нужна только архитектура, она уже в репо. Качать имеет смысл только когда вы **используете их веса** как инициализацию (инференс из коробки или старт для дообучения).

### 1.2 Проверка кода: возможна ли реализация с нуля (summary)

| Компонент | Поддержка «с нуля» | Комментарий |
|-----------|---------------------|-------------|
| **Base DiT** (`LongCatVideoTransformer3DModel`) | **Да, на уровне класса** | Наследует `ModelMixin`, `ConfigMixin` из diffusers → есть `from_config(**config)`, дающий случайную инициализацию. Собственных переопределений `from_pretrained`/`from_config` нет. |
| **Avatar DiT** (`LongCatVideoAvatarTransformer3DModel`) | **Да, на уровне класса** | Аналогично: mixins дают `from_config()`; конфиг совместим с `@register_to_config` и параметрами `__init__`. |
| **train.py** | **Нет** | Всегда вызывается только `from_pretrained(checkpoint_dir, subfolder="dit"|"avatar_single")`. Варианта инициализации по одному конфигу (без весов) нет. При отсутствии весов в `checkpoint_dir` загрузка весов в diffusers приведёт к ошибке. |
| **loader.py** | Не применимо | Только инференс; для инференса «с нуля» не используется. |

**Итог по коду:** архитектура позволяет обучение с нуля (оба класса поддерживают `from_config()` и случайную инициализацию). Текущий **training entrypoint (train.py) пути «только конфиг, без весов» не реализует** — нужен отдельный сценарий (например флаг `--from_scratch` и вызов `Model.load_config(...); Model.from_config(...)` с сохранением текущего формата датасета и цикла обучения).

## 2. Риски использования их весов

| Риск | Оценка | Меры |
|------|--------|------|
| **Лицензия** | **Низкий** | Веса и код LongCat-Video на HuggingFace — MIT. Коммерческое использование разрешено. Товарные знаки/патенты Meituan не передаются — нейтрально для использования весов в своём продукте. |
| **Переносимость** | **Средний** | Формат: Diffusers-совместимый (config.json + safetensors, в т.ч. sharded). Загрузка через `ModelMixin.from_pretrained(path, subfolder="dit")` — уже используется. Риск: изменение формата на HF или переименование ключей в будущих релизах. Мера: хранить снапшот весов у себя (vendor copy), не полагаться на онлайн HF в production. |
| **Контроль embedding space** | **Средний** | Text conditioning: caption_channels=4096, UMT5 — общий с LongCat. Пока используете тот же text_encoder/tokenizer — пространство совместимо. Риск: смена текстового энкодера или изменение длины/формата кондиционирования потребует дообучения/адаптации. Аватар добавляет свой conditioning (audio, identity) — эта часть под вашим контролем. |
| **Масштабирование** | **Низкий** | 13.6B параметров; у вас уже context parallel (Ulysses), multi-GPU инференс и обучение. Масштабирование — за счёт вашего пайплайна, не за счёт репозитория LongCat. |

**Итог по рискам:** лицензия и масштабирование не блокеры. Переносимость и embedding space закрываются снапшотами весов, единой точкой загрузки (`loader.py`) и при необходимости adapter’ом для иных форматов.

## 3. Оптимальная структура проекта для интеграции DiT

### 3.1 Разделение: ядро vs веса vs vendor

- **Ядро (наш код):** всё под `arachne_x/` — pipelines, modules (DiT, VAE, scheduler), loader, audio, streaming. Сюда не класть чужие веса.
- **Веса (checkpoints):** отдельное дерево, только данные. Не коммитить в git (кроме маленьких тестовых артефактов, если нужно).
- **Vendor dependency:** LongCat-Video как «внешний набор весов + эталон формата». Код LongCat в репо не подключаем; используем только веса и конфиг.

Рекомендуемая структура каталогов:

```
<workspace_root>/
  arachne_x/                    # ядро (код)
    __init__.py
    loader.py                   # единственная точка загрузки весов для инференса
    pipeline_arachne_x_video.py
    pipeline_arachne_x_video_avatar.py
    streaming_inference.py
    model_adapter.py            # опционально: конвертация чужих чекпоинтов
    modules/
      longcat_video_dit.py      # base DiT (архитектура)
      avatar/
        longcat_video_dit_avatar.py
      ...
    audio_process/
    context_parallel/
    ...

  scripts/
    train.py                    # загрузка только DiT (subfolder dit / avatar_single)
    infer.py
    download_longcat_video.py   # скачивание vendor-весов

  weights/                      # НЕ в git, .gitignore
    LongCat-Video/              # vendor snapshot (HF meituan-longcat/LongCat-Video)
      dit/
      vae/
      tokenizer/
      text_encoder/
      scheduler/
      ...
    arachnex/                   # свои чекпоинты (обучение, fine-tune)
      base_lora/
      avatar_single/
      avatar_multi/

  checkpoints/                  # альтернатива или дополнение к weights/arachnex
    <run_id>/
      dit/ or avatar_single/

  dit/                          # опционально: только для референса конфига/индекса
                                # лучше не хранить полные веса здесь; оставить только config
                                # или убрать dit/ из корня и брать конфиг из weights/LongCat-Video/dit
```

Итого: **models** = код в `arachne_x/modules/`, **checkpoints** = `weights/` (и при необходимости `checkpoints/`), **pipelines/schedulers** = код в `arachne_x/`, веса — только в `weights/` (vendor vs arachnex).

### 3.2 Как не смешивать чужие веса и ядро

1. **Одна точка входа на загрузку:** только `loader.py` для инференса и только `train.py` для загрузки DiT при обучении. Все пути к директориям весов приходят аргументами (например `checkpoint_dir`, `--checkpoint_dir`), не хардкод путей к конкретным файлам в ядре.
2. **Чёткое именование путей:** например `weights/LongCat-Video` = vendor snapshot; `weights/arachnex/*` или `checkpoints/<run_id>` = свои чекпоинты. В доке и скриптах явно зафиксировать эту схему.
3. **Не класть тяжёлые артефакты в репозиторий:** `weights/` и большие `checkpoints/` в `.gitignore`. Папка `dit/` в корне репо — если там только config/index без самих shards, можно оставить как референс; иначе предпочтительно убрать и брать конфиг из `weights/LongCat-Video/dit`.
4. **Версионирование vendor-снапшота:** при обновлении весов с HF сохранять копию под именем с датой/тегом (например `weights/LongCat-Video-20250220`) и в скриптах/документации указывать, какую версию используете.

## 4. Скачивание модели, vendor dependency, lazy loading

### 4.1 Способ скачивания

| Метод | Плюсы | Минусы |
|-------|--------|--------|
| **snapshot_download (полный)** | Простота, полная совместимость с HF | Скачивается весь репо (включая лишнее) |
| **snapshot_download + allow_patterns** | Только нужные папки (dit, vae, tokenizer, text_encoder, scheduler) | Нужно поддерживать список паттернов при изменении структуры на HF |
| **huggingface-cli download** | Удобно для ручного разового скачивания | Для автоматизации лучше скрипт |
| **Git LFS** | Подходит для своего репо с весами | Для HF репо обычно не используется; HF даёт API/hub. |

**Рекомендация:** оставить `scripts/download_longcat_video.py` как основу и перейти на **selective download** через `snapshot_download(..., allow_patterns=[...])`, чтобы не тянуть лишние файлы (например, демо-скрипты, лишние конфиги). Пример паттернов:

- `"dit/*"`
- `"vae/*"`
- `"tokenizer/*"`
- `"text_encoder/*"`
- `"scheduler/*"`

Так вы явно фиксируете зависимость только от артефактов модели. Остальное (README, примеры и т.д.) при необходимости качать отдельно или не качать.

### 4.2 Хранение как vendor dependency

**Да, хранить отдельно как vendor dependency.**

- В коде не хардкодить путь к HF; указывать только локальный каталог (например `weights/LongCat-Video`).
- В CI/деплое: либо предзалитый снапшот в своё хранилище, либо шаг «скачать через download_longcat_video.py» с указанием версии/тега.
- В документации явно указать: «Base DiT (и при необходимости VAE, tokenizer, …) — vendor: meituan-longcat/LongCat-Video, версия YYYY-MM-DD».

### 4.3 Lazy loading весов

- **Пайплайн:** загрузка уже «ленивая» в том смысле, что веса читаются только при вызове `load_base_pipeline(checkpoint_dir, ...)` или `load_avatar_pipeline(...)`. До этого момента ни один тензор DiT в память не попадает.
- **Внутри DiT:** `ModelMixin.from_pretrained()` загружает все shards, нужные для данной модели (по `diffusion_pytorch_model.safetensors.index.json`). Для ещё более жёсткого lazy (пошаговая подгрузка блоков) потребовалась бы своя обёртка над safetensors с загрузкой по мере forward — трудоёмко и даёт выигрыш только при очень ограниченной памяти; для вашего целевого железа (H200/H100, 110–120 GB VRAM) не обязательно.
- **Рекомендация:** оставить текущую схему загрузки в `loader.py`; при необходимости добавить опцию «загружать только конфиг, веса подгружать по требованию» только если появятся сценарии с нехваткой RAM до загрузки на GPU.

## 5. Fork, переименование, изоляция в adapter-layer

### 5.1 Нужен ли fork репозитория LongCat-Video

**Нет.** В ARACHNE-X уже используется не их репозиторий, а своя реализация архитектуры в `arachne_x/modules/` (longcat_video_dit, blocks, attention, avatar variant и т.д.). Вы зависите только от:

- формата весов (config + safetensors с определёнными ключами);
- соглашения о подпапках (dit, vae, …).

Fork имел бы смысл, если бы вы активно дорабатывали их код обучения/инференса и хотели мержить обратно или поддерживать патчи. Текущая модель — «наша реализация + их веса»; fork не обязателен.

### 5.2 Переименование (naming)

**Рекомендуется постепенно перейти на свой нейминг в публичном API и в новых модулях.**

- Публичный API уже частично свой: `ArachneXVideoPipeline`, `ArachneXVideoAvatarPipeline`, `ArachneXVideoAvatarPipeline` в `__init__.py`.
- Внутри пайплайнов и лоадера по-прежнему фигурируют `LongCatVideoTransformer3DModel`, `LongCatVideoAvatarTransformer3DModel`, `LongCatVideoPipeline`/`LongCatVideoAvatarPipeline`. Для ясности границы «vendor vs наше» можно:
  - ввести алиасы типа `ArachneXDiTBase = LongCatVideoTransformer3DModel` и использовать их в пайплайнах и лоадере;
  - либо переименовать классы в `arachne_x.modules` в `ArachneXDiT3D`, `ArachneXAvatarDiT3D`, оставив совместимость весов (имена параметров в state_dict не менять). Тогда внешний мир видит только ArachneX*, а внутри при загрузке весов ключи остаются те же (blocks.* и т.д.).

Имена файлов (`longcat_video_dit.py`) можно оставить для совместимости с историей и комментариями «LongCat-compatible»; либо переименовать в `dit_3d.py` / `avatar_dit_3d.py` с алиасами старых имён для импортов.

### 5.3 Изоляция кода LongCat в adapter-layer

**Текущее состояние:** их «кода» в репо у вас нет — есть ваша реализация архитектуры, совместимая с их весами. Роль adapter’а выполняет:

- **Единая точка загрузки:** `loader.py` — строит пайплайн, подставляет нужный `checkpoint_dir` и subfolder.
- **model_adapter.py:** конвертация ключей и форматов при загрузке «чужих» чекпоинтов (не в формате HF LongCat). Для стандартных весов HF adapter не обязателен.

Рекомендация: **не выносить текущий DiT в отдельный «vendor adapter» пакет**. Оставить модули в `arachne_x/modules/`, но:

- явно документировать: «Архитектура DiT совместима с весами meituan-longcat/LongCat-Video»;
- при появлении второго источника весов (другая модель, другой формат) — загружать через `model_adapter.py` (конвертация ключей → один и тот же класс `LongCatVideoTransformer3DModel` или будущий `ArachneXDiT3D`).

Таким образом, изоляция — на уровне «пути к весам + опциональный key-adaptation», а не вынос всего DiT в отдельный vendor-пакет.

## 6. Финальная рекомендация: reference vs production backbone vs полная переписывание

| Вариант | Описание | Рекомендация |
|---------|----------|--------------|
| **Reference implementation** | Использовать LongCat только как образец идей, свою реализацию писать с нуля, веса не использовать. | **Нет.** Уже есть рабочая реализация и совместимость весов; повторная реализация 13.6B без весов не даёт выгоды. |
| **Production backbone** | Текущая схема: наша реализация архитектуры в `arachne_x/modules/`, загрузка pretrained весов LongCat для base DiT, свои пайплайны (T2V/I2V/VC/avatar), свой training. | **Да.** Это и есть текущая и целевая модель использования. |
| **Полная переписывание** | Выбросить текущий DiT и написать свой с нуля (другая архитектура). | **Нет.** Теряется совместимость с проверенными весами и усложняется поддержка без явной бизнес-цели. |

**Итоговая рекомендация:** использовать DiT LongCat-Video как **production backbone**: наша кодовая база в `arachne_x/`, их веса — как vendor dependency в отдельном каталоге (`weights/LongCat-Video`), загрузка только через `loader.py` и при обучении через `train.py`. Selective download, явное версионирование снапшота, при необходимости переименование в ArachneX* и сохранение adapter’а только для нестандартных форматов чекпоинтов. Fork и полная переписывание не требуются.

## 7. Краткий чеклист внедрения

- [ ] Вынести пути к весам в конфиг/аргументы; не хранить тяжёлые веса в git.
- [ ] В `download_longcat_video.py` добавить `allow_patterns` для selective download.
- [ ] Зафиксировать в документации: vendor = meituan-longcat/LongCat-Video, версия/дата снапшота.
- [ ] Разделить в `weights/`: `LongCat-Video/` (vendor), `arachnex/` или `checkpoints/` (свои).
- [ ] По желанию: алиасы ArachneX* для DiT-классов и использование их в пайплайнах/loader.
- [ ] Папку `dit/` в корне репо использовать только для конфига/референса или убрать, брать конфиг из `weights/LongCat-Video/dit`.

После этого интеграция DiT остаётся архитектурно чистой, с чёткой границей между ядром ARACHNE-X и внешней зависимостью по весам.
